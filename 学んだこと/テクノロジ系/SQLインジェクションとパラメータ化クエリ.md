# SQLインジェクションとパラメータ化クエリ

## 2026-09-12

### パラメータ化クエリの本質

SQLインジェクション対策で重要なのは、`?` という記号そのものではなく、**SQLの命令部分と、利用者から受け取るデータ部分を分離してDBへ渡すこと**である。

例えば、次のようなSQLを考える。

```sql
SELECT * FROM users WHERE name = ?
```

ここで `?` は、単に「自動的に文字列へ変換する記号」ではない。DBドライバやDBMSが、**ここには後から値が入る**というプレースホルダとして扱う。

まずSQLの構造として、概念的には次の部分が確定する。

```text
SELECT * FROM users WHERE name = [値]
```

その後、別に値を渡す。

```text
値 = ' OR '1'='1
```

重要なのは、この入力値をDBが**SQL文の続きとして再解釈しない**ことである。あくまで `name` と比較する一つのデータ値として扱う。

そのため、攻撃者が次の文字列を入力しても、

```text
' OR '1'='1
```

意味としては次のようになる。

```text
WHERE name = [値: "' OR '1'='1"]
```

DBは「名前が文字通り `' OR '1'='1` という利用者」を探すだけであり、`OR '1'='1'` をSQLの条件式として実行しない。

### 文字列連結との違い

入力値をSQL文字列へ直接連結すると、入力値がSQL文の一部として解析される危険がある。

```text
文字列連結
SQL文 + 入力値 を一本のSQL文字列としてDBへ渡す
→ 入力値がSQLの命令・構文として解釈され得る

パラメータ化クエリ
SQL文の構造を確定する
↓
値をパラメータとして別に渡す
→ 入力値はデータとして扱われ、SQL命令にならない
```

例えば危険な文字列連結では、入力値によって次のようなSQLが組み立てられる可能性がある。

```sql
SELECT * FROM users
WHERE name = '' OR '1'='1';
```

この場合、攻撃者の入力がSQL構文へ入り込み、検索条件そのものを書き換えている。

一方、パラメータ化クエリではSQL構造と値が分離されるため、同じ入力をSQL構文として注入できない。これがSQLインジェクション対策として有効な理由である。

### プレースホルダの書き方はDBやドライバで異なる

本質は `?` ではなく、**命令とデータの分離**である。プレースホルダの表記はDBやドライバによって異なる。

| 例 | プレースホルダの代表例 |
| --- | --- |
| MySQL系の一部ドライバ | `?` |
| PostgreSQL | `$1`, `$2` など |
| SQL Server系 | `@name` など |

したがって、`?` を見たら安全という暗記ではなく、**値をSQL文字列へ連結せず、DBドライバのパラメータ機構で別に渡しているか**を見る。

### XSSとの共通点

SQLインジェクションとXSSには、利用者入力を「データではなくコードとして解釈させてしまう」という共通構造がある。

- **SQLインジェクション**：利用者入力をSQLコードとして解釈させない
- **XSS**：利用者入力をHTMLやJavaScriptコードとして意図せず解釈させない

どちらも、**コードとデータの境界を崩さない**ことが重要である。ただし対策方法は同じではなく、SQLインジェクションではパラメータ化クエリ、XSSでは出力先コンテキストに応じたエスケープなどを使う。

### 覚え方

> パラメータ化クエリ = SQLの命令を先に決めて、値は後から「データ」として渡す。

`?` はそのための予約席の一例であり、SQLインジェクションを防ぐ本質は**SQLの構造と入力値を分離すること**である。
