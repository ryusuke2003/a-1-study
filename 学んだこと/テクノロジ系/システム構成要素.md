# システム構成要素

## 2026-08-28

### キャパシティプランニングの目的

- キャパシティプランニングは、システムの現在の応答時間や利用状況を測定・継続監視し、将来の需要も見込んで必要な処理能力を確保する活動である。
- この問いの正解は **イ**。現在の応答時間を調査し、長期的に監視して将来を含めた応答時間を維持する。
- ボトルネックだけを対象にした改善や、ソフトウェア・ハードウェアのチューニングによる現状性能の最大化は、主に性能チューニングの説明である。リソース過剰利用の解消も、キャパシティプランニングの目的を十分に表していない。

## 2026-08-29

### リバースプロキシの役割

- リバースプロキシは、利用者（クライアント）からの要求を受け取り、背後にあるWebサーバーやアプリケーションサーバーへ転送する中継サーバーである。利用者からは、リバースプロキシが公開サーバーに見える。
- 主な役割は、複数のバックエンドサーバーへの負荷分散、TLS/SSLの終端、応答のキャッシュ、バックエンドサーバーを外部から直接公開しないことによる保護である。
- 通常のフォワードプロキシがクライアント側に置かれて外部サーバーへのアクセスを代理するのに対し、リバースプロキシはサーバー側に置かれてバックエンドへのアクセスを代理する。

### BASE特性をもつ分散NoSQLデータベース

- ネットワーク上に分散した複数ノードで構成され、一つのノードで更新したデータを他ノードへ反映する。
- ノードは、分散システムの中でデータを保存・処理する一つの参加単位であり、通常はサーバー、仮想マシン、コンテナ、又はDBプロセスに相当する。AWSのAZやリージョンはノードを置く場所の区分であって、ノードそのものではない。
- 各ノードに全データのコピーを置く場合もあるが、実際にはデータを分割して保持し、各データを必要な数だけ別ノードへ複製する構成もある。
- BASEは、可用性を重視し、各ノードの状態が一時的に異なり得ることを許容する（Basically Available、Soft state、Eventual consistency）。
- システムに障害がなければ、更新結果は**いずれ**全ノードへ反映される。これは結果整合性（eventual consistency）であり、更新直後に全ノードが同じ結果を返すことは保証しない。
- 2相コミットで全ノードに反映することは、分散トランザクションで整合性を強く保つための方式であり、BASEの結果整合性の説明ではない。
- ノード間のネットワークが分断された場合でも、BASE志向のシステムは可用性を優先して、少なくとも一部のノードで要求を受け付ける設計を取り得る。ただし、分断中はデータの不整合が一時的に生じ得る。
- この問題の正解は **イ**。「システムに障害がなければ、いつかは全てのノードに反映される」は結果整合性を表す。

### 信頼性（reliability）

- 信頼性は、定められた条件・期間にわたって故障せず、要求された機能を正しく果たし続けられる性質である。
- **可用性（availability）**は、必要な時点にシステムを利用できる状態にあるかに着目する。信頼性が高いほど可用性も高まりやすいが、可用性は故障後の修復時間にも左右されるため、両者は同じ意味ではない。

### SOA（Service Oriented Architecture）

- SOAは、利用者・業務の観点でシステム機能を独立したサービスとして分割し、標準化されたインタフェースを通じて組合せ・再利用・連携しやすくするアーキテクチャである。問24の正解は **エ**。
- サービスを独立させることで、業務プロセスとの対応付けや他ソフトウェアとの連携を容易にする。
- サービス指向アーキテクチャのこと

| 選択肢の内容 | 用語 |
| --- | --- |
| 会計・人事・製造などの業務プロセスを一元管理する | ERP |
| 業務要件とパッケージ機能の適合・乖離を分析する | フィット＆ギャップ分析 |
| 業務プロセスへPDCAを適用し、継続的に改善する | BPM |
| 独立したサービスに分割し、組合せ・連携しやすくする | SOA |

### 2相コミット（Two-Phase Commit: 2PC）

- 2相コミットは、複数のサーバーやデータベースにまたがる一つの分散トランザクションについて、全参加者がコミットするか、全参加者が中止（ロールバック）するかをそろえるプロトコルである。これにより原子性（all or nothing）を保つ。
- **第1相（prepare／投票）**では、コーディネータが各参加者にコミット可能かを問い合わせ、参加者は処理結果を確定できる状態にして、コミット可能かを応答する。
- Prepare は「仮確定」に近い状態である。参加者は変更をまだ他の処理から確定済みとして見せず、コミット可能であることをログなどに記録し、必要なロックやリソースを保持して最終指示を待つ。したがって、この時点では全体のコミットは完了しておらず、abort の指示なら中止（ロールバック）する。
- **第2相（commit／abort）**では、全参加者がコミット可能と応答したときだけ、コーディネータが全員にコミットを指示する。一人でも不可なら、全員に中止を指示する。
- コーディネータは手順を調整する主体、参加者は各サーバーやDBなど実際に処理する主体である。コーディネータが障害で停止すると、参加者が最終判断を待ち続けるブロッキングが起こり得る。
- BASEの結果整合性は一時的な不整合を許容して可用性を重視するのに対し、2PCは参加者間の結果をそろえるため、待機や可用性低下のトレードオフを伴い得る。

## 2026-09-01

### フールプルーフ

- **フールプルーフ（foolproof）**は、利用者が誤った操作をしようとしても、危険・不正な操作をできないようにする設計思想である。
- 例として、扉が開いている間は機械を起動できなくする、必須項目が未入力なら確定操作を受け付けない、形状を変えて誤った向きでは差し込めなくする、などがある。
- **フェイルセーフ（fail-safe）**は故障・障害が起きたときに停止・遮断など安全側へ移す設計、**フォールトトレラント**は一部が故障しても機能を継続できるようにする設計であり、フールプルーフとは対象と目的が異なる。

### VDI（Virtual Desktop Infrastructure）

- VDIは、サーバー側の仮想マシン上で利用者ごとのデスクトップ環境を実行し、利用者端末には画面転送を行う方式である。
- データやアプリケーションをデータセンター側へ集約しやすく、端末紛失時のデータ漏えいリスク低減や、デスクトップの一元管理に役立つ。一方で、サーバー・ネットワークの性能や可用性に依存する。

## 2026-09-02

### CSP（Cloud Service Provider）

- **CSP（Cloud Service Provider：クラウドサービスプロバイダ）**は、クラウドサービスを利用者へ利用可能な状態で提供する事業者・組織である。コンピューティング資源やサービスを用意し、契約に基づいて利用者がオンデマンドに使えるようにする主体を指す。
- CSPが提供するサービスは、代表的に **IaaS・PaaS・SaaS** に分けられる。どの層までをCSPが運用し、利用者がどの層を設定・管理するかが異なる。

## 2026-09-06

### 稼働率とMTBF・MTTR

- **MTBF（Mean Time Between Failures：平均故障間隔）**は、修理して利用を再開してから次に故障するまでの平均稼働時間である。長いほど故障しにくい。
- **MTTR（Mean Time To Repair：平均修復時間）**は、故障してから修復して利用を再開するまでの平均時間である。短いほど早く復旧できる。
- 単一の修理可能システムが稼働と修復を繰り返す基本モデルの定常稼働率 \(\alpha\) は、次の式で求める。

  `稼働率 α = MTBF ÷ (MTBF + MTTR)`

- 分子・分母をMTBFで割ると、次のように変形できる。

  `α = 1 ÷ (1 + MTTR ÷ MTBF)`

この式から、稼働率はMTBFとMTTRの個別の値ではなく、**MTTR ÷ MTBFの比**で比較できる。

- `αA = αB` ならば、`MTTRA ÷ MTBFA = MTTRB ÷ MTBFB` である。
- `αA > αB` ならば、`MTTRA ÷ MTBFA < MTTRB ÷ MTBFB` である。
- 稼働率を高めるには、MTBFを長くして故障頻度を下げるか、MTTRを短くして復旧を速める。

したがって、問5で常に成り立つのは **イ** である。稼働率が等しくても、MTBFとMTTRがそれぞれ同じとは限らない。例えば、MTBFとMTTRを同じ倍率で増減しても比と稼働率は変わらない。

| 選択肢 | 判定理由 |
| --- | --- |
| ア | 稼働率が同じでも、MTBFとMTTRの個別の値が同じとは限らない。 |
| イ | 稼働率が等しければ、MTTR ÷ MTBFの比も等しい。 |
| ウ | 稼働率の大小だけでは、MTBFとMTTRそれぞれの大小を同時には決められない。 |
| エ | 稼働率が高いほどMTTR ÷ MTBFは小さいので、不等号の向きが逆である。 |

### プロビジョニング

- **プロビジョニング（provisioning）**は、IT資源やサービスを利用できるように、必要な資源を準備・割当・設定することである。文脈によって、需要を予測してネットワーク設備やシステム資源をあらかじめ調達・増強する活動から、用意済みのクラウド資源を自動で払い出す処理までを含む。画像の設問の正解は **エ**。
- クラウド環境では、テンプレートや自動化によってサーバー・ストレージ・ネットワークなどを迅速かつ一貫して割り当てる。ただし、単に自社設備へ業務パッケージを導入して利用する運用形態を選ぶこと自体は、プロビジョニングの説明ではない。

| 選択肢の内容 | 区別 |
| --- | --- |
| 情報システムの企画・設計・開発・導入・保守を一貫又は工程ごとに提供 | システムインテグレーション（SI）などのサービス提供形態に関する説明であり、個別環境を使える状態にするプロビジョニングではない。 |
| 複数企業・組織が共同でデータセンターを運用してサービスを利用 | 複数組織で利用する共同利用・コミュニティクラウドに近い説明である。 |
| 自社でハードウェア・ネットワークを用意し、業務パッケージを導入して利用 | オンプレミスでのシステム利用形態に関する説明であり、サービス提供のための資源準備を表すプロビジョニングではない。 |
| 需要予測に基づきネットワーク設備やシステム資源を計画的に調達・強化し、要求時に提供できるよう備える | プロビジョニングである。 |

- CSPは、利用者の代わりに全てのセキュリティ責任を負うものではない。例えば、IaaSではCSPが物理設備や基盤を保護する一方、利用者はOS設定、アカウント・権限、アプリケーションや保存データの設定・保護に責任を持つ。責任分担はサービスモデルと契約内容で確認する。
- **クラウド利用者（Cloud Consumer）**はCSPのサービスを利用する主体であり、CSPとは逆の立場である。**クラウドブローカー（Cloud Broker）**は、複数サービスの仲介・統合や利用関係の調整を担う主体で、サービスを実際に提供するCSPそのものとは限らない。**クラウドキャリア（Cloud Carrier）**はCSPから利用者までの接続・転送を仲介する主体、**クラウド監査者（Cloud Auditor）**はサービスや実装を独立に評価する主体である。
- CASBは利用者とクラウドサービスの間でアクセス制御や可視化を行うセキュリティ機能であり、CSPそのものではない。
