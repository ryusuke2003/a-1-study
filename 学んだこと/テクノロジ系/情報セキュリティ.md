# 情報セキュリティ

## 2026-08-29

### 電子証明書の種類と用途

- 電子証明書は、公開鍵と主体（サーバー、利用者、組織、ソフトウェア発行者など）の対応を、認証局（CA）が保証する仕組みである。証明書の種類は、何の身元を確認したいかで区別する。
- **サーバ証明書**は、Webサーバーなどのサーバーの身元（主に接続先ドメイン）を確認するために使う。TLS/HTTPS通信でサーバー認証を行い、通信相手のなりすましを防ぐ。
- **EV SSL証明書**は、サーバ証明書の一種で、認証局が組織の実在性などをより厳格に確認して発行する。WebサイトのHTTPSで使われるが、HTTPSで使う証明書すべてがEVではない。
- **クライアント証明書**は、利用者や端末の身元をサーバーへ示すために使う。パスワード認証に加えて、又は代えてクライアント認証（mTLS）に利用する。
- 具体的には、社内ポータルや管理画面へアクセスする従業員端末の認証、取引先向けB2BシステムやAPIの相互TLS（mTLS）認証、VPN・無線LANの端末認証などで使われる。
- TLS接続時にサーバーがクライアントへ証明書の提示を要求し、クライアントは秘密鍵を保有していることを証明する。サーバーはCAを信頼の起点として、証明書の有効性と利用者・端末の識別子を確認してアクセスを許可する。
- サーバ証明書が「接続先サーバーは正しいか」をクライアントへ示すのに対し、クライアント証明書は「接続してきた利用者・端末は正しいか」をサーバーへ示す。端末へ適切に配布・失効管理することが前提になる。
- **コードサイニング証明書**は、ソフトウェア、アプリ、スクリプトなどに電子署名し、発行元と署名後に改ざんされていないことを確認するために使う。通信相手のサーバー認証用ではない。

### 電子メールの送信元認証と改ざん検知

- **DKIM**は、送信側メールサーバーがメールヘッダーなどにドメインの秘密鍵でデジタル署名を付け、受信側メールサーバーがDNSに公開された公開鍵で検証する仕組みである。この署名が証明するのは、「このメールは少なくとも `example.com` のドメイン側で正当に署名された」ということである。送信元ドメインのなりすましや、送信後のメール改ざんの検知に使う。
- **S/MIME**は、基本的に個人・メールアドレス単位の証明書を使い、その本人がメールへ電子署名したり、受信者の公開鍵で本文を暗号化したりする方式である。個人・組織単位の送信者確認、改ざん検知、本文の秘匿に使う。メールサーバーがドメイン署名を検証するDKIMとは、署名の主体が異なる。
- 覚え方は、**DKIM = ドメイン単位の真正性**、**S/MIME = 個人・メールアドレス単位の真正性**である。DKIMは「そのドメイン側で正当に署名されたメールか」を示すのであり、特定の個人がメール本文を書いたことまで証明するものではない。
- **SPF**は、あるドメインのメール送信を許可されたメールサーバーをDNSで宣言する仕組みである。メール本文・ヘッダーへの署名による改ざん検知は行わない。
- **OP25B**は、迷惑メール送信を抑制するために、プロバイダなどが利用者ネットワークから外部へのTCP 25番ポート通信を制限する対策である。

### メール送信・認証方式の役割分担

| 方式 | 一言でいう役割 | 守る対象・確認すること |
| --- | --- | --- |
| SMTP-AUTH | 送信許可 | メール送信クライアントをSMTPサーバーで認証し、認証されない第三者の中継利用を防ぐ |
| SPF | 送信サーバー確認 | ドメインがDNSで宣言した送信許可サーバーから送られたかを確認する |
| DKIM | ドメイン署名＋改ざん検知 | ドメイン側の署名を検証し、署名対象のヘッダー・本文が送信後に改ざんされていないことを確認する |
| DMARC | SPF/DKIMを使った最終判定ルール | 表示上のFromドメインとの整合も確認し、失敗時の受信側の扱い（監視・隔離・拒否）とレポート方法をDNSで公開する |
| S/MIME | メール内容を個人単位で守る | 個人・メールアドレス単位で電子署名して送信者・改ざんを確認し、受信者の公開鍵で本文などを暗号化して秘匿できる |

- SMTP-AUTHは「利用者がこの送信サーバーから送ってよいか」の認証であり、受信側が送信元ドメインを検証するSPF/DKIM/DMARCとは目的が異なる。
- DMARCは、SPF又はDKIMの認証結果が成功していても、表示上のFromドメインと認証されたドメインが整合しなければDMARCの判定には利用しない。これにより、利用者が目にするFromアドレスのなりすましへの対策を強める。

### サイドチャネル攻撃

- サイドチャネル攻撃は、暗号アルゴリズムそのものを解くのではなく、実装・装置から意図せず漏れる情報を観測して秘密情報を推測する攻撃である。
- 代表例は、処理時間の差を観測するタイミング攻撃、消費電力を測る電力解析、電磁波・音響の観測である。
- 対策は、一定時間で処理する実装、ブラインディング、不要な情報漏えいを抑える実装・遮へいなどであり、暗号方式を強くするだけでは十分でない。

### CASB（Cloud Access Security Broker）

- CASBは、利用者とクラウドサービスの間で可視化・ポリシー適用を担うセキュリティ機能である。
- 未承認クラウド利用の把握、アクセス制御、DLP、脅威検知、コンプライアンス支援などを行う。クラウドサービス自体を提供する仕組みではない。

### HSTS（HTTP Strict Transport Security）

- HSTSは、WebサイトがブラウザへHTTPSだけを使用するよう伝える仕組みであり、Strict-Transport-Securityレスポンスヘッダーでポリシーを通知する。
- ブラウザが有効なHSTSポリシーを保持している間は、HTTPへの接続をHTTPSへ置き換えるため、SSLストリッピングなどHTTPへのダウングレードを抑止する。
- ヘッダーはHTTPS応答で受け取って初めて有効になるため、初回接続時の保護には限界がある。ブラウザのHSTS preload listはこの初回問題を補う手段の一つである。

### 衝突困難性

- 衝突困難性は、ハッシュ関数において、同じハッシュ値になる異なる二つの入力を見つけることが計算量的に困難である性質である。
- これは、ある入力からハッシュ値を求めることが難しい性質（原像計算困難性）や、与えられた入力と同じハッシュ値をもつ別入力を見つけることが難しい性質（第二原像計算困難性）とは区別する。

### smurf攻撃

- smurf攻撃は、送信元IPアドレスを被害者に偽装したICMP Echo Requestをブロードキャストアドレスへ送信し、多数の応答を被害者へ集中させる反射・増幅型のDoS攻撃である。
- ブロードキャスト宛てのICMP応答を抑止することや、送信元IPアドレス詐称をフィルタリングすることが対策になる。

### CAAレコード

- CAA（Certification Authority Authorization）レコードは、ドメイン所有者が、そのドメインの証明書発行を許可する認証局（CA）をDNSで指定するレコードである。
- 公開Web PKIのCAは証明書発行前にCAAを確認する。CAAはCAによる誤発行リスクを抑えるための発行時の制御であり、ブラウザが証明書を検証する仕組みではない。

### NTLM・チャレンジレスポンスとPass-the-Hash

- **NTLM（NT LAN Manager）**は、主にWindowsで用いられてきた古い認証プロトコルである。現在のActive Directory環境ではKerberosが標準的な認証方式であり、NTLMは互換性などの理由で残る場合がある。
- NTLMは、パスワードの平文をネットワークへ送らず、サーバーが送る予測不能な**チャレンジ（nonce）**に対して、クライアントがパスワードから得られる**NTハッシュ**を基に計算した**レスポンス**を返すチャレンジレスポンス方式である。サーバー又はドメインコントローラーは、登録済みの資格情報から同じ計算をして照合し、本人性を確認する。
- この方式は平文パスワードの盗聴を抑えるが、NTハッシュは認証計算に使える長期の秘密情報である。端末のメモリ、資格情報データベース、バックアップなどからNTハッシュを窃取されると、平文パスワードを復元しなくても悪用され得る。
- **Pass-the-Hash（PtH）攻撃**は、窃取したNTハッシュをそのまま認証に使い、平文パスワードを知らずに対象アカウントになりすます攻撃である。特に管理者権限のNTハッシュを取得されると、Windows環境で他端末・サーバーへ横展開される危険がある。これはハッシュ関数を解読する攻撃ではなく、ハッシュが認証の秘密情報として受け入れられることを悪用する攻撃である。
- 対策は、Kerberosを優先して**NTLMの利用を削減・制限**する、Credential Guardなどで資格情報を保護する、管理者アカウントの共用を避け最小権限・管理者権限の分離を行う、ローカル管理者パスワードを端末ごとに異ならせる、不要な管理共有・リモート管理を制限し、異常な認証を監視することである。MFAは重要だが、既存のNTLM認証がMFAを経由しない経路ではPtHを単独では防げない。

### LSASS・Credential Dumpingと資格情報の悪用

- **LSASS（Local Security Authority Subsystem Service）**は、Windowsで認証、ログオン、ローカルセキュリティポリシー、資格情報の処理を担う中心的なプロセスである。KerberosやNTLMの認証処理に関係し、ログオン状況によってはNTLM関連の資格情報や、KerberosのTGT・サービスチケットなどがメモリ上に存在し得る。
- **Credential Dumping（資格情報ダンピング）**は、OS内部に保存又は一時保持される認証情報を不正に取得する攻撃である。LSASSのメモリだけでなく、SAMデータベース、レジストリに保護された資格情報、ドメイン環境のキャッシュされた資格情報などが標的になり得る。資格情報を直接得られなくても、パスワードハッシュやチケットなど認証に使える情報が窃取対象となる。
- 窃取した**NTLMハッシュ**はPass-the-Hashに、**Kerberosチケット**はPass-the-Ticketに悪用される。Pass-the-Ticketは、窃取した有効なTGT又はサービスチケットを使い、平文パスワードを入力せずにKerberos認証済みの利用者としてサービスへアクセスする攻撃である。平文パスワード又は有効な資格情報を取得された場合も、他端末・サーバーへの横展開につながる。
- 対策は、最小権限と特権アカウントの分離により、そもそも高権限の資格情報が一般端末へ残らないようにすることが基本である。Credential GuardやLSASS保護を有効化して資格情報の窃取を困難にし、EDRでLSASSへの不審なプロセスアクセス・メモリダンプ作成を検知する。加えて、NTLMを削減しKerberosを適切に運用する、MFAを導入する、管理者アカウントの利用・ログオン先を制限する。

### クリプトジャッキング

- クリプトジャッキングは、攻撃者が他者の端末・サーバー・ブラウザの計算資源を無断で暗号資産の採掘に使う行為である。
- 端末の高負荷、電力消費、サービス性能低下などを招く。マルウェア対策、脆弱性対策、リソース監視が対策となる。

### トランザクション署名とMITB攻撃

- トランザクション署名は、振込先・金額など取引内容を含めて利用者が署名・確認する仕組みである。ログイン認証だけでなく、個々の取引の改ざん検知・承認に用いる。
- MITB（Man-in-the-Browser）攻撃は、端末に感染したマルウェアがブラウザ内で表示や送信内容を改ざんし、正規利用者の操作を悪用する攻撃である。
- トランザクション署名をブラウザとは別の信頼できる画面・端末で確認することで、MITBによる振込先・金額の差し替えを検出しやすくなる。

### ISMAP

- ISMAP（政府情報システムのためのセキュリティ評価制度）は、政府が利用するクラウドサービスについて、政府が求めるセキュリティ要求を満たすことを評価し、登録する制度である。
- 政府機関等は原則としてISMAPクラウドサービスリストに登録されたサービスから調達する。ISMAPは個別システムの脆弱性診断や、民間の認証制度一般を指すものではない。

### SMTP-AUTHとOCSP

- SMTP-AUTHは、メール送信クライアントがSMTPサーバーへ認証してからメールを送信するためのSMTP拡張である。認証されていない第三者によるメール中継（オープンリレー）の悪用を防ぐ。
- SMTP-AUTHは送信サーバーへの利用者認証であり、メール本文の暗号化・電子署名や、送信ドメイン認証（SPF/DKIM/DMARC）とは目的が異なる。
- OCSP（Online Certificate Status Protocol）は、証明書の失効状態をOCSPレスポンダへ問い合わせて確認するプロトコルである。証明書失効リスト（CRL）をまとめて取得する方式と比べ、個別の証明書状態を問い合わせられる。

### ビヘイビア法とフォールスポジティブ

- ビヘイビア法（行動的生体認証）は、キーストロークの間隔、マウス操作、歩行など、利用者の行動特性で本人を識別・認証する方法である。指紋や顔など身体的特徴を用いる方式とは区別する。
- フォールスポジティブ（偽陽性）は、本来は異常でないものを異常と誤って判定することをいう。対になるフォールスネガティブ（偽陰性）は、異常を正常と誤って見逃すことである。

### カミンスキー攻撃とテンペスト攻撃

- カミンスキー攻撃は、DNS問い合わせのトランザクションIDと送信元ポート番号を推測・総当たりして偽のDNS応答を送り、DNSキャッシュを汚染する攻撃である。
- ランダム性の高い送信元ポート番号とトランザクションIDの利用、DNSSECの利用などが対策となる。
- テンペスト攻撃は、機器が発する電磁波などを傍受・解析して、画面表示や処理内容などの情報を盗み見る攻撃である。遮へい、距離の確保、漏えいを抑えた設備が対策となる。

### FIPS 140とPGP

- FIPS 140は、暗号モジュールのセキュリティ要件と検証を定める米国連邦標準であり、現行版はFIPS 140-3である。暗号アルゴリズムを実装しているだけではなく、対象の暗号モジュールとして検証を受ける点が重要である。
- PGP（Pretty Good Privacy）は、公開鍵暗号と共通鍵暗号を組み合わせ、メールやファイルの暗号化・電子署名に利用する仕組みである。電子署名では送信者確認・改ざん検知、暗号化では内容の秘匿を目的とする。

### HMACと電子署名

- HMAC（Hash-based Message Authentication Code）は、送信者と受信者だけが共有する秘密鍵とハッシュ関数からメッセージ認証コードを作る方式である。受信者は同じ共有秘密鍵で検証し、メッセージの改ざん検知と、共有鍵を知る相手から届いたことの確認を行う。
- HMACを検証できる者は共有秘密鍵を知っている必要がある。したがって、検証者もHMACを生成でき、第三者に対して「特定の送信者だけが作成した」と証明する用途には適さない。共有鍵の安全な配布・保管が前提である。
- 電子署名は、署名者だけが持つ秘密鍵で署名を作り、対応する公開鍵を知る誰でも検証できる。署名対象の改ざん検知に加え、公開鍵が証明書などで署名者と結び付けられていれば、第三者を含む多数の検証者へ署名者を示せる。
- つまり、HMACは共有秘密を持つ当事者間の認証、電子署名は公開鍵で広く検証可能な真正性の確認に向く。どちらも通常はメッセージそのものを秘匿しないため、内容を隠すには別途暗号化が必要である。

### ビットコインのマイニング

- ビットコインの**マイニング**では、マイナーが未確定取引を検証して候補ブロックにまとめ、Proof of Work（PoW）の条件を満たすハッシュ値を見つける計算競争を行う。PoWは、ブロックヘッダーに含めるナンスなどを変えながら、ネットワークが定めた難易度以下のハッシュ値を探す仕組みである。
- 最初に有効なPoWを見つけたマイナーは候補ブロックをネットワークへ送る。各ノードが取引の署名・残高・二重支払いの有無やPoWを検証し、有効と認めれば既存のブロックチェーンの末尾へ連結する。この手順により取引記録の順序についてネットワークの合意を形成する。
- ブロックを生成したマイナーは、ブロック内の特別な取引による**新規発行分（ブロック補助金）**と、そのブロックに含めた取引の**手数料**を報酬として受け取れる。これは、計算資源を提供して取引の検証・記録に参加する経済的な動機になる。
- ブロックが一つ追加された時点で取引の巻戻しが絶対に不可能になるわけではない。後続ブロックが積み重なり、その取引の確認数が増えるほど、過去の記録を書き換えるために必要な計算量が大きくなり、実用上の確定性が高まる。

### Identity-Aware Proxy（IAP）

- **Identity-Aware Proxy（IAP）**は、Google CloudでWebアプリケーションや仮想マシンへのアクセスの手前に置かれ、利用者の**認証**とリソースごとの**認可**を行うプロキシ型のアクセス制御サービスである。利用者は保護対象へ要求を送る前にIAPでIDを確認され、IAMなどで許可された利用者だけがアプリケーションやリソースへ到達できる。
- IAPは、ネットワークへ広く接続させる従来のVPNと異なり、アプリケーション又はリソース単位でアクセスを許可する。利用者ID・グループ・端末のセキュリティ状態・接続元IPアドレスなどのコンテキストに基づいて、最小権限のアクセス制御を適用でき、ゼロトラストの考え方に合う。
- Cloud Run、App Engine、Compute Engine、GKE上のアプリケーションなどを保護できる。IAPのTCP転送では、SSHやRDPなどの管理アクセスにも認証・認可を適用し、仮想マシンへ直接公開IPアドレスやインターネットからの管理ポートを必ずしも公開せずに済む。
- IAPを有効にするだけで、保護対象への全ての直接経路が自動的に遮断されるわけではない。IAPを経由しないバックエンド到達経路をファイアウォールやネットワーク設計で適切に制限し、IAPをバイパスできないようにする必要がある。

### セキュアWebゲートウェイ（SWG）

- **セキュアWebゲートウェイ（SWG: Secure Web Gateway）**は、組織の利用者・端末とインターネットの間でWeb通信を中継・検査し、組織のセキュリティポリシーを適用する仕組みである。利用者が危険なWebサイトや不正なコンテンツへアクセスすること、又は端末から機密情報が外部へ送信されることを抑止する。
- 主な機能は、URL・ドメインのカテゴリに基づくアクセス許可／遮断、ダウンロードファイルなどのマルウェア検査、Webアプリケーションの利用制御、通信内容の検査によるDLP（情報漏えい防止）である。暗号化されたHTTPS通信の内容を検査するには、組織が管理する端末で証明書を配布するなどしてTLS復号・再暗号化を行う構成がある。これはプライバシー、証明書管理、通信性能への影響も考慮して適用する。
- **CASB**は主にクラウドサービスの利用可視化・アクセス制御・SaaS上のデータ保護を担い、**SWG**はより広く利用者からインターネットへのWeb通信をフィルタリングする。**IAP**は組織が保護するアプリケーションへの入口で認証・認可を行うのに対し、SWGは利用者が外部Webへ出る通信を制御する。
- SWGはクラウド型又はオンプレミス型で提供され、リモートワーク端末の通信もSWGへ転送することで、社内・社外で一貫したWebアクセス制御を適用できる。SSE／SASEでは、SWGはCASBやZTNAなどと組み合わせる代表的な機能の一つである。

### パディングオラクル攻撃

- **パディングオラクル攻撃**は、CBCモードなどで暗号化されたデータを攻撃者が少しずつ改変してサーバーへ送り、復号後のパディングが正しいかどうかによるエラー内容・HTTP応答・処理時間などの違いを観測して、平文を推測する攻撃である。ここで、パディングの成否を答えてしまう復号側の振る舞いを「オラクル」と呼ぶ。
- CBC復号では、あるブロックの平文は「その暗号文ブロックの復号結果」と「直前の暗号文ブロック（先頭ブロックではIV）」の排他的論理和で得られる。したがって、攻撃者が直前ブロック又はIVを変えると、次の平文ブロックを意図した値へ変化させられる。正しいパディングになったかという反応を繰り返し観測することで、バイト単位で平文を絞り込める。
- 対策は、改ざんを検証する前に復号・パディング処理を進めない**認証付き暗号（AEAD）**を使うことであり、AES-GCMやChaCha20-Poly1305などを選ぶ。CBCを扱う必要がある場合は、暗号文へMACを付けて復号より先にMACを検証し、パディングエラーと認証エラーを区別しない応答・一定時間に近い処理を行う。ただし、応答を一律にするだけでなく、暗号方式・実装をAEADへ移行することが望ましい。

### CBC（Cipher Block Chaining）モード

- **CBC**は、ブロック暗号で平文をブロック単位に暗号化する際、各平文ブロックへ直前の暗号文ブロックを排他的論理和（XOR）で混ぜてから暗号化する連鎖方式である。つまり、最初のブロック以外は `C_i = E_K(P_i XOR C_{i-1})` となる。前の暗号文ブロックが次の平文ブロックに影響する点が「Chaining」である。
- 先頭ブロックには直前の暗号文ブロックがないため、予測不能な**初期化ベクトル（IV）**を用いる。先頭は `C_1 = E_K(P_1 XOR IV)` として暗号化する。IVを暗号化のたびに異なる値にすれば、同じ鍵・同じ先頭平文ブロックを暗号化しても毎回同じ暗号文になることを防げる。復号時は `P_i = D_K(C_i) XOR C_{i-1}`、先頭は `P_1 = D_K(C_1) XOR IV` である。
- CBCでは暗号文ブロック又はIVを書き換えると、復号後の対応する平文へ影響が及ぶ。この性質が、パディングの成否を外部へ漏らす実装と組み合わさると、パディングオラクル攻撃につながる。CBCそのものは改ざん検知を提供しないため、現在は暗号化と認証を同時に行うAEADを選ぶことが望ましい。

### スキミング

- **スキミング**は、クレジットカードやキャッシュカードなどに記録されたカード番号・有効期限・磁気ストライプ情報などを、本人に気付かれないよう不正に読み取って取得する行為である。盗んだ情報は、偽造カードの作成やオンラインでの不正利用に悪用されるおそれがある。
- 代表例は、ATMや決済端末に取り付けた不正な読み取り装置で磁気ストライプ情報を取得する方法や、改ざん・侵害された決済端末からカード情報を窃取する方法である。暗証番号を狙う場合には、周囲の盗撮など別の手段と組み合わせられることがある。スキミングは情報の不正取得であり、不正な決済実行そのものとは区別する。
- ICチップは取引ごとに利用される情報を変化させる仕組みを使えるため、磁気ストライプの複製だけに依存する決済より偽造に強い。ただし、ICカードでもカード番号などを入力するオンライン取引への悪用や、端末改ざんなどのリスクがなくなるわけではない。
- 対策として、利用者はATM・決済端末の不自然な部品や挿入口を確認し、暗証番号入力時に手元を隠す、利用明細・利用通知を確認して不審な取引を速やかに届け出る。事業者側ではIC対応、端末の改ざん検知・定期点検、カード情報を保存しない又はトークン化するなどを行う。

### MITM（Man-in-the-Middle）攻撃

- **MITM（Man-in-the-Middle）攻撃／中間者攻撃**は、攻撃者が利用者とサーバーなどの通信経路の間に割り込み、双方になりすまして通信を盗聴、改ざん、又は別の相手へ転送する攻撃である。攻撃者は利用者とサーバーの間に二つの別セッションを作り、それぞれに正規の相手であるかのように振る舞う。
- 公衆Wi-Fiなど信頼できないネットワークでの不正な中継、通信先の名前解決の偽装、暗号化されていないHTTP通信をHTTPSへ切り替えさせないダウングレードなどが、MITMにつながる。攻撃が成功すると、ログイン情報・個人情報の盗聴や、振込先・送信内容などの改ざんが起こり得る。
- 対策の基本は、TLS/HTTPSで通信を暗号化し、クライアントがサーバー証明書の信頼性・有効期限・接続先ホスト名を正しく検証することである。証明書警告を安易に無視しない、HSTSでHTTPへのダウングレードを抑止する、重要な用途ではクライアント証明書を用いた相互認証（mTLS）を利用する、安全性が確認できないネットワークではVPNなどを利用することが有効である。
- MITMが通信**経路上**に割り込むのに対し、MITB（Man-in-the-Browser）攻撃は利用者端末に感染したマルウェアがブラウザ内部で通信内容を改ざんする。TLSはMITM対策に有効でも、端末内で暗号化前・復号後の情報を操作するMITBだけでは防げない。

### リプレイ攻撃

- **リプレイ攻撃**は、攻撃者が通信を盗聴して取得した正規の認証要求・取引要求・署名付きメッセージなどを、内容を改ざんせずに再送し、受信側に同じ処理をもう一度実行させようとする攻撃である。例えば、正規の送金要求を再送して二重に処理させたり、過去の認証メッセージを再利用してなりすましたりする。
- メッセージの暗号化、MAC、電子署名は、内容の秘匿・改ざん検知・真正性確認に役立つが、過去に正当に作成された同一メッセージの再送まで自動では見分けられない。リプレイ対策には、各要求が一回限り又は有効期間内であることを受信側が判定できる情報が必要である。
- 代表的な対策は、受信側が毎回発行する予測不能な**ノンス**を応答へ含めて一度だけ受け入れるチャレンジレスポンス、**タイムスタンプ**と短い有効期限の検査、要求ごとの**シーケンス番号**や一意なトランザクションIDを記録して重複を拒否する方法である。タイムスタンプ方式では時刻同期と許容時間幅の管理も必要になる。

### NOTICE（National Operation Towards IoT Clean Environment）

- **NOTICE**は、総務省・NICT・インターネットサービスプロバイダ（ISP）などが連携し、サイバー攻撃に悪用されている、又は悪用されるおそれがあるIoT機器を調査し、利用者へ注意喚起してセキュリティ対策を促す取組である。インターネット接続されたルーターやネットワークカメラなどを対象とする。
- NICTは、弱い又は初期設定のID・パスワードでログインできる機器、脆弱なファームウェアを搭載する機器、マルウェア感染が疑われる機器などを調査する。該当機器の情報はISPなどへ提供され、ISPが契約者を特定して、パスワード変更、ファームウェア更新などの対策を注意喚起する。
- 目的は、IoT機器の乗っ取りとボットネット化を抑え、DDoS攻撃などのサイバー攻撃に悪用されるリスクを減らすことである。これはOSSの著作権表示を収録するNOTICEファイルとは別の意味である。
