# データベース

## 2026-08-29

### 関係データベースのビュー

- ビューは、基の表（実表）に対する問合せから定義する仮想的な表である。必要なデータだけを利用者へ見せるために使える。
- `SELECT` で列を選び、`WHERE` で条件を指定して行を絞り込んだビューを定義できる。ビューは列だけを抜き出すものではない。
- ビューの列名は、基の表の列名とは異なる名称（別名）で定義できる。
- 二つ以上の表を結合したビューは、結合方法などの条件によって更新できない場合がある。「結合によるビューは必ず更新できる」は誤りである。
- 和集合演算（`UNION`）を用いたビューも定義できる。
- この問題の正解は **ア**。

## 2026-09-06

### 第1・第2・第3正規形の見分け方

データベースの正規化は、**一つの表に混ざっている情報を、意味ごとに分けて重複や不整合を減らすこと**と考えると分かりやすい。

#### まず主キーとは

- **主キー**は、表の中の1行を一意に特定するために選ぶキーである。
- 1つの表で主キーとして選ぶものは1つだが、その主キーが**複数の列の組合せ**になることはある。このような主キーを**複合主キー**という。
- 例：成績表で `学生ID` だけでは同じ学生の複数科目を区別できず、`科目ID` だけでも複数学生を区別できない場合、`学生ID + 科目ID` を主キーにする。
- 主キーになれる候補が複数ある場合、それらを**候補キー**と呼び、その中から1つを主キーとして選ぶ。

#### 正規化問題で出る用語をやさしく言い換える

- **候補キー** = **1行を特定できるキー**。主キーとして選べる候補。
- **候補キーの一部** = **複合キーを作っている列の一部分**。例えば候補キーが `学生ID + 科目ID` なら、`学生ID` だけ、又は `科目ID` だけを指す。
- **候補キー以外の属性** = **1行を特定するためのキーではない普通の列**。例えば `学生名`、`科目名`、`学部名` など。
- **関数従属性** = **「Aが決まればBも一意に決まる」関係**。`A → B` と書く。例えば `学部ID → 学部名` は、学部IDが分かれば学部名が決まるという意味。

問題文を読むときは、難しい用語を次のように置き換えると理解しやすい。

- `候補キーの一部 → 候補キー以外の属性` = **複合キーの片方だけで普通の列が決まる**
- `候補キー以外の属性 → 別の候補キー以外の属性` = **普通の列を見れば別の普通の列が決まる**

この言い換えを使うと、第2正規形と第3正規形の違いを判別しやすい。

#### 第1正規形

- **第1正規形（1NF）**は、1つのセルに複数の値を入れないようにする。
- 例えば `履修科目 = 数学, 英語` のように1セルへ複数値を入れず、数学の行と英語の行に分ける。
- 覚え方は **「1マス1値」**。

#### 第2正規形

- **第2正規形（2NF）**は、第1正規形を満たした上で、**複合主キーの一部だけで決まる列**を別表へ分ける。
- つまり、主キー全体ではなく、その一部分だけに依存する**部分関数従属**をなくす。
- 第2正規形は、主キーを1列にする操作ではない。分解後も複合主キーがそのまま残る表は普通にある。

例：

| 学生ID | 科目ID | 学生名 | 科目名 | 点数 |
|---|---|---|---|---|
| 001 | M01 | 田中 | 数学 | 80 |
| 001 | E01 | 田中 | 英語 | 90 |

この表の主キーが `学生ID + 科目ID` のとき、

- `学生名` は `学生ID` だけで決まる
- `科目名` は `科目ID` だけで決まる
- `点数` は `学生ID + 科目ID` の両方がないと決まらない

したがって、学生名と科目名は複合主キーの一部だけに依存しているため、学生表・科目表へ分ける。

第2正規形の感覚は、**「主キーの一部分にだけぶら下がっている列を追い出す」**である。

#### 第3正規形

- **第3正規形（3NF）**は、第2正規形を満たした上で、**主キー以外の列を経由して決まる列**を別表へ分ける。
- つまり、非キー属性が別の非キー属性を通じて候補キーに依存する**推移的関数従属**をなくす。

例：

| 学生ID | 学生名 | 学部ID | 学部名 |
|---|---|---|---|
| 001 | 田中 | A | 工学部 |

ここでは、

- `学生ID → 学部ID`
- `学部ID → 学部名`

なので、`学生ID → 学部ID → 学部名` という依存関係になっている。

`学部名` は主キーの `学生ID` から直接決まるというより、非キー属性の `学部ID` を経由して決まっている。そこで、

- 学生表：`学生ID, 学生名, 学部ID`
- 学部表：`学部ID, 学部名`

に分ける。

第3正規形の感覚は、**「主キー以外の列にぶら下がっている列を追い出す」**である。

#### 第2正規形と第3正規形の違い

ここが最重要。

- **第2正規形**：`複合主キーの一部 → 非キー属性` という依存をなくす
- **第3正規形**：`非キー属性 → 別の非キー属性` という依存をなくす

感覚的には、

- 第2正規形で**部分的な依存**をなくす
- 第3正規形で**非キー属性を経由する間接的な依存**までなくす

と考えるとよい。ただし、正確には「直接・間接」よりも**何に依存しているか**で区別する。

| 正規形 | 何をなくすか | 見分け方 |
|---|---|---|
| 第1正規形 | 1セル内の複数値 | 1マス1値か |
| 第2正規形 | 複合キーの一部への依存 | 主キーの一部分だけで決まる列がないか |
| 第3正規形 | 非キー属性どうしの依存 | 主キー以外の列を見れば別の列が決まっていないか |

問9は第2正規形から第3正規形への変換を尋ねているので、**候補キー以外の属性間に関数従属性がある場合に関係を分解する「イ」**が正解である。

| 選択肢 | 対応する考え方 |
| --- | --- |
| ア | 非キー属性から候補キーの一部への依存であり、第3正規形へ変換する通常の説明ではない。 |
| イ | 非キー属性間の関数従属性、すなわち推移的関数従属を除く第3正規化である。 |
| ウ | 複合候補キーの一部から非キー属性への部分関数従属を除く第2正規化である。 |
| エ | 一つの属性に入った複数の値を単一の値へ分ける第1正規化である。 |

覚え方は、**第1＝1マス1値、第2＝キーの一部への依存を除く、第3＝非キー属性同士の依存を除く**である。

### 外部キーと親・子テーブル

- **外部キー（FOREIGN KEY）**は、**別のテーブルの行を指し示すための列**と考えると分かりやすい。
- 例えば `受注.商品コード` が `商品.商品コード` を参照しているなら、`受注.商品コード` が外部キーである。
- **参照される側が親テーブル、参照する側が子テーブル**。この例では `商品` が親、`受注` が子である。
- 外部キー制約を設定すると、親テーブルに存在しない値を子テーブルから参照することを防ぎ、**参照整合性**を保てる。例えば商品表に `C999` が存在しないなら、受注表へ `商品コード=C999` を登録できないようにできる。
- 1つの子テーブルが複数の外部キーを持ち、複数の親テーブルを参照することもある。例えば受注表が商品、顧客、担当者をそれぞれ参照する構成である。

イメージは **「外部キー = 他のテーブルへのリンク」**、**「参照される側が親、参照する側が子」** と覚える。

### 外部キーのON DELETE動作

- `ON DELETE` は、外部キーで参照している**親行を削除したとき、子行をどう扱うか**を指定する。
- `ON DELETE CASCADE`を指定すると、参照されている親行を削除したとき、その親行を参照する子行もデータベースが自動的に削除する。

問10では、親表が「商品」、子表が「受注」であり、`受注.商品コード`が`商品.商品コード`を参照している。削除した商品と同じ商品コードをもつ受注行も自動削除するには、次のように指定する。

```sql
FOREIGN KEY (商品コード) REFERENCES 商品(商品コード)
ON DELETE CASCADE
```

したがって正解は **ア（CASCADE）** である。

| 指定 | やさしい意味 | 親行を削除しようとしたときの動作 |
| --- | --- | --- |
| `CASCADE` | 親を消したら、関連する子も消す | 参照している子行も自動削除する |
| `RESTRICT` | 子が残っているなら親を消させない | 参照する子行が存在する場合、親行の削除を拒否する |
| `SET NULL` | 子は残し、外部キーだけ空にする | 子行の外部キーをNULLにする。外部キー列がNULLを許容する必要がある |
| `SET DEFAULT` | 子は残し、外部キーを既定値へ変える | 子行の外部キーを既定値にする。既定値が定義され、参照制約を満たす必要がある |

`SET NULL` は、親が消えても子の行自体は残したいが、参照先がなくなったことを `NULL` で表したい場合に使う。`SET DEFAULT` は、参照先が消えたときに `UNKNOWN` などの既定の参照先へ付け替える設計で使える。既定値を外部キーとして使う場合、その値が参照先として有効である必要がある。

`CASCADE`は関連データをまとめて消せる一方、意図しない大量削除につながる可能性があるため、実システムではデータの意味と削除方針に合わせて選ぶ。
