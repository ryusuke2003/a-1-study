# データベース

## 2026-08-29

### 関係データベースのビュー

- ビューは、基の表（実表）に対する問合せから定義する仮想的な表である。必要なデータだけを利用者へ見せるために使える。
- `SELECT` で列を選び、`WHERE` で条件を指定して行を絞り込んだビューを定義できる。ビューは列だけを抜き出すものではない。
- ビューの列名は、基の表の列名とは異なる名称（別名）で定義できる。
- 二つ以上の表を結合したビューは、結合方法などの条件によって更新できない場合がある。「結合によるビューは必ず更新できる」は誤りである。
- 和集合演算（`UNION`）を用いたビューも定義できる。
- この問題の正解は **ア**。

## 2026-09-06

### 第1・第2・第3正規形の見分け方

データベースの正規化は、データの重複や、更新・追加・削除時の不整合を減らすために、関数従属性に基づいて関係を適切に分解することである。

- **第1正規形（1NF）**：一つの属性に複数の値や繰返し項目を持たせず、各属性値を単一の値（原子的な値）にする。
- **第2正規形（2NF）**：第1正規形を満たした上で、候補キーの一部だけに非キー属性が依存する**部分関数従属**を取り除く。主に複合候補キーがある場合に問題となる。
- **第3正規形（3NF）**：第2正規形を満たした上で、非キー属性が別の非キー属性を通じて候補キーに依存する**推移的関数従属**を取り除く。

例えば、`社員番号 → 部署番号`、`部署番号 → 部署名` が成り立つ場合、`社員番号 → 部署名` は部署番号を介した推移的関数従属である。社員表と部署表に分けることで、第3正規形にできる。

問9は第2正規形から第3正規形への変換を尋ねているので、**候補キー以外の属性間に関数従属性がある場合に関係を分解する「イ」**が正解である。

| 選択肢 | 対応する考え方 |
| --- | --- |
| ア | 非キー属性から候補キーの一部への依存であり、第3正規形へ変換する通常の説明ではない。 |
| イ | 非キー属性間の関数従属性、すなわち推移的関数従属を除く第3正規化である。 |
| ウ | 複合候補キーの一部から非キー属性への部分関数従属を除く第2正規化である。 |
| エ | 一つの属性に入った複数の値を単一の値へ分ける第1正規化である。 |

覚え方は、**第1＝値を一つずつ、第2＝キーの一部への依存を除く、第3＝非キー属性同士の依存を除く**である。

### 外部キーのON DELETE動作

- **外部キー（FOREIGN KEY）**は、子表の列が参照する値を、原則として親表の主キー又は一意キーに存在する値へ制限し、表間の参照整合性を保つ。
- `ON DELETE CASCADE`を指定すると、参照されている親行を削除したとき、その親行を参照する子行もデータベースが自動的に削除する。

問10では、親表が「商品」、子表が「受注」であり、`受注.商品コード`が`商品.商品コード`を参照している。削除した商品と同じ商品コードをもつ受注行も自動削除するには、次のように指定する。

```sql
FOREIGN KEY (商品コード) REFERENCES 商品(商品コード)
ON DELETE CASCADE
```

したがって正解は **ア（CASCADE）** である。

| 指定 | 親行を削除しようとしたときの動作 |
| --- | --- |
| `CASCADE` | 参照している子行も自動削除する。 |
| `RESTRICT` | 参照する子行が存在する場合、親行の削除を拒否する。 |
| `SET NULL` | 子行の外部キーをNULLにする。外部キー列がNULLを許容する必要がある。 |
| `SET DEFAULT` | 子行の外部キーを既定値にする。既定値が定義され、参照制約を満たす必要がある。 |

`CASCADE`は関連データをまとめて消せる一方、意図しない大量削除につながる可能性があるため、実システムではデータの意味と削除方針に合わせて選ぶ。
