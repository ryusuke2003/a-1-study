# システム開発技術

## 2026-08-29

### UML（Unified Modeling Language）

- UMLは、ソフトウェアシステムを視覚的にモデル化し、構造・振る舞い・利用者との関係などを共通の記法で表すための統一モデリング言語である。
- 要件定義や設計で、関係者間の認識を合わせ、システムの構造や動作を整理・伝達するために使う。
- UMLには、対象に応じてユースケース図、アクティビティ図、シーケンス図、クラス図、オブジェクト図、状態遷移図、コンポーネント図、配置図など複数の図がある。

### UML図の対象

- **ユースケース図**は、システムが提供する機能（ユースケース）と、その機能を利用する人・外部システム（アクター）との関係を表す。「誰が何を使うか」を見る図である。
- **アクティビティ図**は、処理・活動の流れ、分岐、合流、並行処理などを表す。「処理そのものがどう流れるか」を見る図である。
- **シーケンス図**は、オブジェクトやシステム間で交換するメッセージを時系列に沿って表す。「誰と誰が、どの順番で呼び出し・応答するか」を見る図で、通常は上から下へ時間が進む。
- **クラス図**は、クラスの属性・操作と、クラス間の関連・継承など、システムの静的な型・構造を表す。
- **オブジェクト図**は、ある時点に存在する具体的なオブジェクト（クラスのインスタンス）と、オブジェクト間のリンクを表す。クラス図が型を表すのに対し、オブジェクト図はその型から生成された実体のスナップショットを表す。
- **状態遷移図**は、対象が取り得る状態と、イベントを契機にした状態間の遷移を表す。「状態が何をきっかけにどう変わるか」を見る図である。
- **コンポーネント図**は、ソフトウェアを構成するモジュール・コンポーネントと、それらの依存関係・提供／要求インタフェースを表す。
- **配置図**は、サーバー・端末などの物理又は仮想ノードと、その上へ配置するソフトウェア成果物を表す。「どの機器・実行環境に何を置くか」を見る図である。

### 見分け方

| 問われる対象 | 問題文の手掛かり | UML図 |
|---|---|---|
| 誰がどの機能を使うか | 利用者、アクター、機能 | ユースケース図 |
| 処理そのものがどう流れるか | 処理、分岐、並行、フロー | アクティビティ図 |
| システム間のやり取りの順番 | 時系列、メッセージ、呼出し、応答 | シーケンス図 |
| データやクラスの静的な型・構造 | クラス、属性、操作、関連、継承 | クラス図 |
| ある時点の具体的なインスタンス | オブジェクト、実体、リンク、スナップショット | オブジェクト図 |
| イベントによる状態の変化 | 状態、イベント、遷移 | 状態遷移図 |
| ソフトウェア部品の構成・依存関係 | モジュール、部品、コンポーネント、インタフェース | コンポーネント図 |
| ノードと配置物の対応 | サーバー、端末、ノード、配置 | 配置図 |

### 混同しやすい図の区別

- **アクティビティ図とシーケンス図**：処理の分岐・並行を含む業務や制御の流れならアクティビティ図、複数の登場主体間でメッセージをやり取りする時間順序ならシーケンス図である。
- **クラス図とオブジェクト図**：クラス図は型としての属性・操作・関連を表し、オブジェクト図は特定時点に生成済みのインスタンスと具体値・リンクを表す。
- **コンポーネント図と配置図**：コンポーネント図はソフトウェア内部の部品構成、配置図は物理・仮想ノードと配備されるソフトウェアの対応を表す。

### デザインレビューの目的

- **デザインレビュー（設計レビュー）**は、設計工程で作成した仕様書、設計書、図面などの成果物を関係者が確認し、要求との不一致、機能不足、矛盾、実現性・安全性・保守性などの問題を早期に発見して改善する活動である。
- 目的の中心は、後工程へ進む前に**設計工程の成果物にある問題点を発見すること**なので、問16の正解は **ア** である。
- 設計者だけでなく、開発者、テスト担当者、運用担当者、利用部門、有識者など複数の視点を入れることで、設計者本人が見落とした問題も発見しやすくなる。ただし、デザインレビューを品質保証部門だけが行うサンプリング検査と考えるのは誤りである。
- レビュー結果を工程の承認判断に利用する場合はあるが、成果物の合否判定だけが目的ではない。また、プロジェクトマネジメントのプロセスを監査する活動とも異なる。

| 選択肢 | 判定理由 |
| --- | --- |
| ア | 設計工程で設計成果物の問題点を発見するデザインレビューの説明である。 |
| イ | 合否判定だけを目的とせず、品質保証部門だけが行うものでもない。 |
| ウ | プログラムのサンプリング検査ではなく、設計成果物を対象に関係者が確認する。 |
| エ | プロジェクト管理プロセスの問題発見はプロジェクト監査などの領域であり、設計レビューの直接の目的ではない。 |

### システム開発における請負型と準委任型

- **請負型**は、受注者が仕事・成果物を完成させることを約束し、その完成した結果に対して報酬を受ける契約形態である。仕様に基づく設計書やプログラムなど、完成させる成果が明確な業務に向く。
- **準委任型**は、法律行為ではない業務を適切な注意を払って遂行することを委託する契約形態である。業務の遂行に責任を負うが、原則として請負のような仕事の完成そのものを目的としない。ユーザーとベンダーが共同で検討し、ユーザーの判断をベンダーが支援する業務に向く。

「情報システム・モデル取引・契約書＜第二版＞」に基づく問25の整理は、次のとおりである。

| フェーズ | 記号 | 適切とされる契約形態 |
| --- | --- | --- |
| 要件定義 | a | **準委任型** |
| システム外部設計 | - | 準委任型又は請負型 |
| システム内部設計 | b | **請負型** |
| ソフトウェア設計・プログラミング・ソフトウェアテスト | - | **請負型** |
| システム結合 | c | **請負型** |
| システムテスト | - | 準委任型又は請負型 |
| 運用テスト | d | **準委任型** |

準委任型となるのは **aとd** なので、正解は **イ** である。

- **要件定義**では、業務上必要な要件を決定する責任はユーザー側にあり、ベンダーは専門家として整理・検討を支援するため、準委任型とされる。
- **運用テスト**でも、実際の業務で利用可能かをユーザーが主体となって確認し、ベンダーが支援するため、準委任型とされる。
- **システム内部設計、製作、システム結合**は、仕様に基づいた成果物を完成させる性格が強いため、請負型とされる。
- **システム外部設計とシステムテスト**は、業務の範囲、役割分担、成果完成の約束の有無に応じて準委任型又は請負型となる。

この対応は、全ての実務契約が工程名だけで自動的に決まるという意味ではない。実際には、業務内容、完成させる成果物、ユーザーとベンダーの責任分担を契約で明確にする必要がある。

覚え方は、**ユーザーが決める・確認する工程をベンダーが支援するなら準委任、仕様に基づいて成果物を完成させるなら請負**である。

### 業務フローを表すアクティビティ図

- **UMLのアクティビティ図**は、処理や業務の流れを表し、**分岐・合流・並行処理・同期**などを表現できる図である。
- 令和6年度秋期 高度試験 午前I 問25では、「業務要件定義で業務フローを記述し、処理の分岐や並行処理、処理の同期などを表現できる図」が問われているので、正解は **ア：アクティビティ図**。

```text
開始
 ↓
受付
 ↓
◇ 条件分岐
├─ 条件A → 処理A ─┐
└─ 条件B → 処理B ─┤
                   ↓ 合流
                 完了
```

- 並行処理ではフォークで一本の流れを複数へ分け、ジョインで複数の流れがそろうのを待って同期させる。

| 選択肢 | 何を表す図か | 問25での判断 |
| --- | --- | --- |
| **ア アクティビティ図** | **処理・業務の流れ、分岐、並行、同期** | **正解** |
| イ クラス図 | クラスの属性・操作、関連、継承など静的な構造 | 業務フローそのものではない |
| ウ 状態マシン図 | 一つの対象がどの状態を取り、イベントでどう状態遷移するか | 処理フロー全体とは着眼点が違う |
| エ ユースケース図 | 利用者・外部システムと、システムが提供する機能との関係 | 詳細な処理順序・並行処理は表さない |

#### 見分け方

- **処理がどう流れる？** → アクティビティ図
- **どんな部品・型がある？** → クラス図
- **一つの対象がどんな状態へ変わる？** → 状態マシン図
- **誰がどの機能を使う？** → ユースケース図
